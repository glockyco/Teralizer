# Teralizer Improvement Roadmap (toward beating JARVIS)

**Goal.** Produce *better* generalization results than JARVIS (VMCAI 2018) — broader
case handling and higher value/parameter coverage — by removing Teralizer's
**self-inflicted** limitations. Companion: `2026-06-26-jarvis-case-coverage.md`
(the JARVIS investigation + SPF spike that motivates this).

This is a living roadmap of barriers and promising directions with a suggested
order — **not** detailed per-item plans. Detailed design happens when we pick a
target. Nothing here is ruled out; the research-grade items are flagged, not
dropped.

## Reality check & revised priorities (2026-06-26 — supersedes the waves below)

Verified against the implementation + a strategy pass with the lead.

**Why the paper was rejected:** primarily **RQ6 — real-world applicability (only
~1.7% of RepoReapers projects complete processing)**, plus heavy critique for the
**missing JARVIS comparison**. RQ1's modest 1–4pp was *not* the primary reason. So
the response is: (1) **beat JARVIS** — a clean "better by design than SOTA" result
answering the comparison critique; (2) **lift RQ6 applicability** via the
*self-inflicted* exclusion drivers (not external infra). Mutation-score
effectiveness is NOT the focus.

### Verified implementation state (checked, not assumed)
- **#10 double-bounds bug is MOOT for Teralizer.** Teralizer runs SPF in
  `symbolic.collect_constraints=true`; custom commit `b5d4e2c` makes
  `PathCondition.solve()`/`simplify()` early-return in that mode — **the solver is
  never invoked**. Inputs are generated by jqwik from the collected path condition,
  not by the SPF solver, so `makeRealVar`'s `Double.MIN_VALUE` lower bound never
  applies. It only bit spf-eval's *full-symbolic* runs. (Real bug in SPF; irrelevant
  to Teralizer.) **Retracted as a priority** (supersedes the #10 row below).
- **Oracle is a REGRESSION oracle** (expected ← SPF-derived `outputJava`,
  `TestGeneralizationTask:324-327`; original input preserved as the first sample).
  Correct for mutation detection; not independent of the impl (fine — bug-finding out).
- **`char`/`boolean` still absent** from `SUPPORTED_TYPES` (confirmed).
- **`FastMath.abs` (and Precision's ulps path) still degrade** via
  `doubleToRawLongBits` *even in collect-constraints mode* — the symbolic attribute is
  dropped at the native call, so the extracted *output spec* is a constant. #11 (abs
  model) stays relevant; Precision stays blocked (concede).

### Strategy (impact-realism)
- **Bug-finding: OUT.** JARVIS's bug results are cherry-picked, need manual
  true/false-positive triage, and single-version "bugs" are over-approximation FPs.
  → drop #18-as-bug, #16, #17, differential-oracle/Interval.
- **RQ6 is partly external grind.** Much of the ~1.7% is dependency-resolution /
  build / project-structure failure (low "approach merit"). Chase the
  *self-inflicted, approach-relevant* drivers instead.
- **Avoid array/string/object inputs (#2):** mostly surfaces shadowed-loop issues
  (hard research) → low net gain.
- **MUT-id (#5): do the bigger shares** (#6 assertion types 41% + Spoon classpath
  33%); the MUT-id fix itself is **Ghafari mutator/inspector classification**, not a rewrite (~15% true share).

### Revised order
1. **Beat JARVIS (headline contribution):** #1 char+boolean · #11 FastMath.abs
   model · #3 object-construction *scoped to fixed-arity inline construction* · #19
   listener-NPE fix · build the **PVC/IC measurement harness**. Demonstrate
   path-exact specs beat JARVIS's template abstraction on PVC for ~8/10 cases.
2. **Lift RQ6 applicability (the rejection reason) — self-inflicted drivers:**
   #4 interprocedural assertions (NoAssertions 41.3% real-world, ~86% false
   positives — the single biggest self-inflicted applicability killer) · #6
   assertion types + Spoon classpath resolution · #9 @ParameterizedTest.
3. **Deferred / low net gain:** #10 (moot), #2 inputs (loops), #5 MUT-id (Ghafari mutator/inspector fix, not a rewrite),
   #18/#16/#17, constraint-encoding/mutation-effectiveness (RQ1 not the rejection
   reason; revisit only if a mutation story is needed), side-effects/#15, #12-14.

## Evidence ledger (DB-grounded, 2026-06-26)

First-hand read-only queries on `postgres_dev`/`postgres_test`. Decisions cite
these, not headlines. **Method rule:** `filter_result` short-circuits at the first
REJECT, so a fix's *true* reach = cases where it is the first reject AND they pass
the *later* filters (esp. ParameterType, AssertionInLoop). Always net out shadowing.

- **char/boolean reach is mostly shadowed.** Real-world boolean-return rejects =
  12,332, but only ~1,500 have a generalizable param (1,279 numeric / 83 char / 130
  boolean); **3,789 have NO params** and **7,051 only object/String params** →
  shadowed by ParameterType. char-return rejects = 201. In curated `commons-utils`,
  char/boolean rejects ≈ 0 (corpus pre-filtered to numeric). **Verdict:** add
  char+boolean to remove an embarrassing *stated limitation*, but it is NOT an
  applicability mover (~12% of the boolean headline survives shadowing).
- **The real-world applicability ceiling is object/string/state predicates**, not
  the scalar type set. boolean methods are mostly predicates on objects/strings
  (`hasNext()`, `supports(Class)`, `matches(String,…)`) gated by object/string
  inputs or object state (the hard, loop-shadowed territory). ParameterType rejects
  60,289 real-world. Honest RQ6 ceiling — cheap fixes won't move it much.
- **Constructor-param generalization (the #3 mechanism) unshadows only ~2.7% of the
  shadowed boolean predicates.** Of the 12,332 boolean-return rejects, inline
  construction with a scalar literal arg = ~337 (90 receiver `new T(…n…)` + 247 arg
  `new T(…n…)`); 172 are no-arg ctors, 281 non-scalar ctor args, and **11,542 (94%)
  have a field/variable receiver** (object set up via `@Before`/factory/builder/an
  earlier statement). So inline ctor-param gen (#3) is justified by the **JARVIS
  object cases** + a *small* real-world bonus; the real mass (field/var receivers)
  needs **stateful-setup / interprocedural-state** handling (overlaps #15/#8), and
  even the 337 often have the scalar incidental (`new TestMessage(MessageType.X, 0)`
  → behavior driven by the enum). Evidence via `tested_method_call_source_code`.
- **RQ6 measured-failure landscape** (`v_project_failures`): dependency-resolution
  (329) + compile (171) are **PRE-EXCLUDED** (not measured). Measured drivers: "all
  tests excluded" (129 → test-level filters; NoAssertions dominant per RQ6) and "all
  generalized excluded" (269, downstream), plus timeouts (~88), Spoon (6), structure.
- **RepoReapers applicability funnel (where it dies).** Projects 1161 → 507 analyzed
  → 44 w/ ≥1 included assertion → **11 complete** (~1.7% of eligible). Tests 81,834
  → 33,390 included. **Assertions 122,166 → 711 included (0.58%)** — the collapse is
  at the *assertion* level. Of ~121k excluded assertions, **27% have 1 blocker, 62%
  have 2, 10% have 3** → ~73% need *multiple* coordinated fixes; any single fix is
  marginal. Dominant blocker combos: `ParameterType+ReturnType` 31,679 ·
  `MissingValue+UnsupportedAssertion` 25,113 · `MissingValue` 21,616 ·
  `MissingValue+ParameterType` 11,393 · `ParameterType` 8,326 · `ReturnType` 2,299
  (+ ~20k `ExcludedTest` cascades from test-level cuts). Type filters **DEFER** when
  the MUT is unresolved, so the MissingValue masses are partly type-shadowed too.
  **Reading:** >½ of excluded assertions hit the *type ceiling* (object/string
  params and/or returns); the rest are MUT-unresolved/unsupported-assertion (which,
  once fixed, mostly convert to type rejects). **No cheap fix moves this >
  marginally** — substantial RepoReapers progress requires string + object types
  (inputs, outputs, oracles) + stateful setup, all of which hit the loop/
  summarization research wall. Higher-ROI: the JARVIS comparison + characterizing
  the barrier, not chasing the 1.7%.
- **Project-structure failures are concrete + fixable.** "Main/Test compiled path
  `target/classes|test-classes` does not exist" (vote-no-filme, time2lib, UFMGame,
  lovelmslms2_cartier, …) → Teralizer hardcodes Maven default output paths.
  "sources/tests not found" (ShackServer, zoeey, mapzen-android-demo, lajolla,
  lbm-webapp) → non-standard/android/web layouts. **General fix:** detect compiled +
  source/test paths from the POM (`outputDirectory`/`testOutputDirectory`) or by
  search, with an optional per-project path config (ship configs for affected
  dataset projects) — flexible, not per-project hand-tuning. Modest count; removes a
  hardcoded-assumption limitation.

## Thesis: most barriers are self-inflicted, not SPF limits

The paper frames the primary barrier as *type-support limitations of symbolic
analysis* — "SPF cannot extract complete constraints for strings, arrays, and
objects" (`03-approach-03-spec-extraction.tex` L124-128; `02-background.tex`
§symbolic-analysis; `07-conclusions.tex` L29-31). **Our own later evidence
contradicts the blanket claim:**

- SPF type-support study (`~/Projects/phd-thesis/projects/spf-eval/RESULTS.md`):
  SPF **fully** handles int/long/short/byte/**char**/**boolean**; **String**
  (equals/length/concat/substring/charAt/indexOf); **arrays** (+varargs);
  **objects** (lazy init, field read/write, construction); boxed types; ArrayList;
  static fields; switch; loops; recursion; interprocedural calls. *Partial:*
  double/float (a fixable bounds bug). *Genuinely hard:* NaN/signed-zero (needs
  QF_FP), transcendentals, a few unmodeled String methods (compareTo/isEmpty).
- JARVIS spike (`.../jarvis-spike/jarvis-spf-RESULTS.md`): SPF extracts usable
  specs for 8/11 JARVIS cases, **including object-construction + instance methods
  + char** — the shapes Teralizer excludes.

So the dominant barriers are **(a) Teralizer's conservative type/method scoping
and (b) a deliberately basic static-analysis layer** — both mostly engineering.
The paper concedes this (`07-conclusions.tex` L35-38: "Other limitations … are
addressable through engineering improvements without requiring research advances:
interprocedural analysis would recover assertions in helper methods").

## Win condition: what "beat JARVIS" means (pin before any code)

The metric reorders the work, so declare it first.

- **Metric = PVC + capability, NOT mutation score.** JARVIS is scored on parameter
  value coverage (PVC) + instruction coverage (JARVIS Table 2). Our paper already
  disclaims the mutation comparison ("Direct comparison with JARVIS is not
  possible …; we use mutation score rather than PVC", `04-evaluation-04-rq1.tex`
  L9-14). Fight the head-to-head on **capability coverage + PVC**; keep mutation
  score for the separate applicability story.
- **Definition.** Beat JARVIS = (i) capability: ≥10/10 Table-2 cases enter the
  pipeline; (ii) PVC ≥ JARVIS on SPF-amenable cases; (iii) bug-finding parity only
  on the exception/precondition class (see concessions).
- **Concede — Interval (paradigm limit).** MATH-1256 is a *silent wrong-value* bug
  (`new Interval(0.0,-1.0).getSize()` → −1.0), **not** an exception. JARVIS finds
  it by learning the oracle from example pairs (`|y−z|=x`) *independent* of the
  implementation; Teralizer derives the oracle *from* the implementation via SPF
  (`getSize()==upper−lower`), so a negative-size input **matches** our oracle → the
  test passes → bug not surfaced. We post a higher PVC than JARVIS on Interval but
  do **not** reproduce its bug (PVC win + bug-finding loss). Close it only via the
  differential oracle (Optional A).
- **Concede — Precision** (JARVIS's flagship example). BLOCKED on the ulps
  fast-path (`doubleToRawLongBits` concretizes); core `|x−y|≤eps` is extractable,
  ulps needs QF_FP (#17). Frame as the structural-disadvantage case.
- **Non-issue — NaN.** JARVIS cannot sample NaN either; the SPF NaN gap (#17) is
  **shared**, so it is NOT needed to win.
- **Measurement to build.** IC exists (`jacoco_coverage_report`; finer per-test
  collection needed for exact Table-2 replication). PVC is new but small: record
  the values the generated jqwik PBT feeds the MUT (property/supplier hook or jqwik
  `Statistics`) and count distinct; original values are already in
  `assertion.tested_method_call_arguments`. Match JARVIS's PVC definition (1-way
  vs t-way), tries budget (100), and seed.

**Key:** the biggest *resolvable* SPF-stage bucket is exception-path capture
(#18), not a solver-model gap. Resource limits (PC/depth/OOM/timeout) are tunable,
not missing models. `doubleToRawLongBits` concretization (Abs/Precision-ulps) is
**absent here** — it silently degrades the spec rather than crashing, so it never
reaches `EXECUTE_JPF FAILED` (visible only as degenerate specs, per the spike).

## Recommended order (refined with oracle critique, 2026-06-26)

Two goals optimize different metrics, scored separately: **(A) beat JARVIS** =
capability + PVC; **(B) broad yield** = applicability % (RQ5/RQ6), which barely
moves the mutation headline (RQ1: strong/dev suites ≈ +0.05pp; real movement comes
from weak EvoSuite baselines + the Math mutator). Spine: **A first** — the only
clean head-to-head superiority claim, already 8/11 de-risked — then B.

**Move 0 — pin the win condition (free; first).** See "Win condition" above:
metric = capability + PVC (not mutation); concede Interval + Precision; NaN shared.
Without this, Phase 1 is an overclaim.

**Phase 1 — the head-to-head (mostly LOW/MED; verify on the `jarvis_*` harness).**
1. **#10 double/float bounds-bug fix** (LOW, jpf-symbc) — *first code move*, a
   **validity gate**: without it every double case samples only the positive
   half-space, so a "PVC win" measures half the domain (7–8/10 cases).
2. **#1 char + boolean** in `SUPPORTED_TYPES` (LOW) — flips isAscii/isPrintable.
3. **#11 FastMath.abs model + native-math recipe** (LOW) — Abs BLOCKED→FULL;
   reused for transcendentals/sqrt + silent `doubleToRawLongBits` cases.
4. **#19 listener-NPE fix** (LOW) — free recoveries; de-noises the harness.
5. **#3 object-construction inputs, SCOPED to inline construction** (MED) — flips
   Interval + 3×Polynomial + (with #11) Abs. SPF half done (spike); work =
   symbolize ctor args in `JpfInstrumentationTask` + a constructing generator.
   **Fence off** stateful/builder setup (that is #15/#8) to keep it MED, not research.
6. **#18 exception-path capture** (MED) — completes toIntExact's exception path;
   the only axis where Teralizer can match JARVIS bug-finding; also the largest
   real-world SPF bucket (827 dev), bridging into Phase 2.
- **Build the PVC/IC measurement harness** (the scoreboard) alongside Phase 1.

*Honest post-Phase-1 scoreboard:* ~7 clean PVC wins (char×2, min/max×2, poly×3),
toIntExact partial, Interval = PVC-win/bug-loss, Precision = blocked — a defensible
"beat JARVIS on coverage for ~8/10 with two understood caveats."

**Phase 2 — broad applicability (score as applicability %, ~0 mutation headline).**
7. **#4 interprocedural assertion analysis** — biggest test-level lever (41.3%
   NoAssertions, ~86% false positives); prerequisite for helper-delegated MUT-id.
8. **#6 more assertion types** — 41% of MissingValue is unsupported-assertion-type,
   not MUT-id; pair with #5.
9. **#5 MUT-id — adopt Ghafari mutator/inspector classification (static/Spoon, NOT
   from-scratch) + Spoon classpath-resolution sub-task** — do it WITH #4+#6 or its real
   ~15% share (not 57.9%: 41% is #6, 33% is classpath) is shadowed.

**Phase 3 — breadth / deep.** #2 string/array/object inputs → #9 @ParameterizedTest
→ #7 void → #16 toIntExact cast-oracle → #8 side-effects/UIF + #15 call sequences →
#12 multi-test reduction → #13 PIT isolation → #14 Gradle/structure → **#17 QF_FP/NaN
last** (shared gap; only if a concrete case demands it).

## Validation strategy (no eval-DB mutation)

- **JARVIS scoreboard (Phase 1):** `jarvis_*` spike harness for SPF-side changes
  (cases flip BLOCKED/PARTIAL→FULL); a **PVC/IC measurement harness** on the
  generated PBTs vs JARVIS Table 2 (matched tries budget + seed).
- **Applicability (Phase 2):** pipeline on a **scratch DB** / throwaway config
  against JARVIS-era commons-math 3.5 + EqBench — never the collected
  `postgres_dev` / `postgres_test`. Report assertion-generalization rate.
- Mutation score is for the applicability narrative only, not the JARVIS claim.

## Needs real design before implementation (flag for later)

#3 (ctor-args-as-inputs instrumentation + constructing generator; fence to inline
construction), #2 (string/array/object input representation), #5 (Ghafari
mutator/inspector MUT-id + classpath resolution), #8 (side-effect/UIF modeling), #15 (call
sequences), #18 (how an exception becomes a spec: implicit precondition vs
assertThrows-style negative). Each gets its own spec/plan when scheduled.

## Optional strategic directions (distinct contributions; do not fold in)

- **A. Differential oracle — closes the Interval class.** Carry the original test's
  asserted constant as an *independent* oracle alongside the SPF-derived one. A
  generated negative-size Interval then contradicts the *test's* expectation even
  though it matches the implementation → reproduces JARVIS's semantic-bug finding.
  The principled way to truly beat JARVIS on Interval.
- **B. Constraint-encoding depth (compound terms, e.g. `a == b+1`).** Constraint
  utilization is 11–69% (`05-discussion`); the largest *effectiveness* lever when
  generalization applies, cutting TooManyFilterMissesExceptions — the path to a
  mutation-score story on weak-baseline datasets.
